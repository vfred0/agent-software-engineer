== Enums

Los enums se definen en `core/enums/` y se usan para valores fijos tipados.

=== Estructura de Enum con Opciones y BadgeColor

Cada enum puede tener un array de `Option<T>` que incluye `badgeColor` (de Kobiq `KbqBadgeColors`) para usar con `app-option-badge`.

[source, typescript]

== Models

Los modelos y DTOs están en `core/models/`. Se dividen en:
- *Auth Models*: `access-token.dto.ts`, `session.ts`, `sign-in-request.dto.ts`
- *Filter Models*: `search-criteria.ts`, `activity.filter.ts`, `date.filter.ts`

=== Interfaz `Option<T, D>` (`core/utils/utils.ts`)

Define la estructura para opciones de selects y badges:

[source, typescript]
----
export interface Option<T, D = unknown> {
  id: T;                    // Valor único (usualmente enum o string/number)
  name: string;              // Texto mostrado
  image?: string;             // URL de imagen (opcional)
  badgeColor?: KbqBadgeColors; // Color del badge (de Kobiq)
  isPositive?: boolean;        // Si es positivo (opcional)
  options?: Option<T>[];     // Sub-opciones (para optgroups)
  description?: string;       // Descripción (opcional)
  roles?: Role[];            // Roles que pueden verlo (opcional)
  data?: D;                  // Datos adicionales (genérico)
  append?: (value: unknown) => void; // Función para extender (si es ExtendableOptions)
}
----

=== Función `createExtendableOptions<T>` (`core/utils/utils.ts`)

Crea un array de opciones que puede extenderse dinámicamente:

[source, typescript]
----
export function createExtendableOptions<T>(options: Option<T>[]): ExtendableOptions<T> {
  const optArray = [...options] as ExtendableOptions<T>;

  optArray.append = function (newItems: T[] | Option<T>[]): Option<T>[] {
    const existingIds = new Set(this.map((opt) => opt.id));

    const mappedOptions = newItems.map((item) => {
      if (item !== null && typeof item === 'object' && 'id' in item && 'name' in item) {
        return item as Option<T>;
      }
      return { id: item as T, name: String(item) } as Option<T>;
    });

    const additions = mappedOptions.filter((opt) => !existingIds.has(opt.id));
    this.push(...additions);
    return this;
  };

  return optArray;
}
----

Uso práctico:
[source, typescript]
----
// En el componente padre
allergyOptions = AllergyOptions.append(this.panelData.user?.allergies || []);

// En la plantilla (select multiple)
<app-select
  formGroupKey="allergies"
  [options]="allergyOptions()"
  [multiple]="true"
/>
----

=== Función `getOptionByValue` (`core/utils/utils.ts`)

Encuentra una opción por su valor:

[source, typescript]
----
export function getOptionByValue(value: unknown, options: Option<unknown>[]): Option<unknown> {
  return options.find((option) => option?.id === value) || options[0];
}
----

== Mocks

Los datos de prueba están en archivos `.mock.ts` en `core/`. Pueden exportar **interfaces (DTOs)** o **clases**:

=== Cuándo usar Clases vs Interfaces

- *Interface/DTO plano*: Cuando el objeto es solo datos, sin lógica interna.
- *Clase*: Cuando necesitás **procesamiento interno** (ej. constructor que mapea relaciones, valida datos, inicializa colecciones). Usar clases aumenta la **cohesión** (datos + comportamiento juntos) y el **encapsulamiento** (lógica oculta dentro del objeto).

=== Ejemplo: `treatments.mock.ts` (Clases para cohesión)

Exporta clases `TreatmentExam`, `TreatmentSession`, y `TreatmentDto` con lógica en el constructor:

[source, typescript]
----
import { TreatmentComplexity, TreatmentSessionStatus, TreatmentStatus } from '@core/enums/treatment.enum';
import { DateTime } from 'luxon';

// Clase para examenes dentales - maneja su propia inicialización
export class TreatmentExam {
  id!: number;
  treatmentSessionId!: number;
  type!: TreatmentExamType;
  date!: DateTime;
  fileUrl!: string;
  interpretation?: string;

  constructor(init?: Partial<TreatmentExam>) {
    Object.assign(this, init); // Mapeo de datos
  }
}

// Clase para sesiones - maneja colecciones internas
export class TreatmentSession {
  id!: number;
  appointmentId!: string;
  startDate!: DateTime;
  endDate!: DateTime;
  notes!: string;
  status!: TreatmentSessionStatus;
  exams?: TreatmentExam[];

  constructor(init?: Partial<TreatmentSession>) {
    Object.assign(this, init);
    // Lógica interna: si vienen exams, los instancia como clases
    if (init?.exams) {
      this.exams = init.exams.map((exam) => new TreatmentExam(exam));
    }
  }
}

// DTO principal - maneja sesiones como clases
export class TreatmentDto {
  id!: number;
  userId!: number;
  status!: TreatmentStatus;
  description!: string;
  complexity!: TreatmentComplexity;
  sessions?: TreatmentSession[];
  // ... más campos

  constructor(init?: Partial<TreatmentDto>) {
    Object.assign(this, init);
    // Encapsula el mapeo de sesiones
    if (init?.sessions) {
      this.sessions = init.sessions.map((session) => new TreatmentSession(session));
    }
  }
}

== Patrones Observados==

- Los enums exportan tanto el enum crudo como las opciones para selects (`*Options` suffix).
- Los DTOs se definen junto con los mocks en el mismo archivo o archivo cercano.
- `SearchCriteria` es el contrato común entre exploradores, servicios y filtros.

=== Mocks: Interface vs Clase (Cohesión y Encapsulamiento)

Se usa **interface** cuando el objeto es solo datos (DTO plano) sin lógica interna.

Se usa **clase** cuando necesitás **procesamiento interno** (ej. mapear colecciones, validar datos, inicializar estado). Esto:
1. **Aumenta la cohesión**: Mantiene datos y comportamiento relacionado juntos en la misma unidad.
2. **Mejora el encapsulamiento**: Oculta la lógica de inicialización y transformación dentro del constructor, evitando usar getters externos o lógica dispersa.

Ejemplo de cohesión en `treatments.mock.ts`:
- `TreatmentSession` tiene un constructor que, si recibe `exams`, los instancia como `new TreatmentExam(exam)`.
- `TreatmentDto` hace lo mismo con `sessions`.
- El consumidor solo hace `new TreatmentDto(init)` y obtiene un objeto con todo configurado, sin necesidad de getters o lógica externa.
